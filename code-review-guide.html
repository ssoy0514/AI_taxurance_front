큰 그림 한눈에 보기

이 프로젝트는 삼성생명 FC(보험설계사)가 상품 정보, 보장설계 화법, 약관, 언더라이팅 기준 등을 AI의 도움을 받아 빠르게 찾아보고, 숏츠·팟캐스트 형태의 교육 콘텐츠도 함께 볼 수 있는 “영업 지원 포털”입니다.

비유로 이해하기

프론트엔드(이 저장소)는 손님을 맞는 “홀”입니다. 메뉴판을 보여주고, 주문을 받고, 음식이 나오면 예쁘게 세팅해서 손님에게 가져다주는 역할을 하죠.

백엔드(사내 API 서버)는 실제로 요리를 하는 “주방”입니다. 상품 데이터를 찾고, AI에게 질문을 던지고, 결과를 만들어 홀로 넘겨줍니다.

이 저장소는 홀의 코드만 담고 있습니다. 즉, 화면에 무엇을 어떻게 보여줄지를 다루고, 실제 데이터를 만들어내는 “요리” 자체는 다른 서버(주방)가 담당합니다.

이 앱이 제공하는 6가지 핵심 기능

기능메뉴 위치한 줄 설명
상품나침반/sales/product-info상품을 고르면 AI가 채팅으로 상세 설명·상담 멘트를 생성
보장설계 바이블/sales/design-bible고객 조건(성별·나이·관심보장)을 넣으면 AI가 맞춤 화법을 생성

약관조회/sales/terms상품·기간·특약별 약관 원문을 검색하고 AI 요약을 확인

폴더 구조 — 무엇이 어디에 있나

Nuxt는 폴더 이름 자체에 규칙과 의미를 부여합니다. 폴더 이름만 알아도 그 안의 파일이 대략 무슨 역할인지 짐작할 수 있습니다.

pages/ → 화면(페이지) 정의. 파일 하나 = URL 하나 ├─ main.vue 메인 홈 (심플 버전) ├─ mainNew.vue 메인 홈 (카드형 신버전, 목데이터 사용) ├─ play.vue 영상/오디오 재생 페이지 ├─ podcast.vue 팟캐스트 목록 ├─ shorts.vue 숏츠 영상 목록 ├─ error.vue 에러 화면 진입점 └─ sales/ ├─ product-info.vue 상품나침반 ├─ design-bible.vue 보장설계 바이블 ├─ terms.vue 약관조회 └─ under.vue 간편 언더라이팅 components/ → 여러 페이지가 재사용하는 부품 (25개) layouts/ → 페이지들을 감싸는 공통 뼈대 store/ → 앱 전체가 공유하는 데이터 (Vuex) plugins/ → 앱이 켜질 때 한 번 실행되는 초기화 코드 middleware/ → 페이지 진입 전 실행되는 “검문소” server-middleware/ → 서버(Node) 쪽에서만 도는 코드 utils/ → 여러 곳에서 쓰는 순수 함수 모음 assets/styles/ → 전역 디자인 규칙 (SCSS) static/ → 가공 없이 그대로 배포되는 파일 nuxt.config.js → 이 프로젝트 전체 설정의 시작점 package.json → 실행/빌드 명령어 & 라이브러리 목록
🗂️

핵심 규칙 한 가지 — pages 폴더에 .vue 파일을 하나 추가하면, 별도 설정 없이 그 파일명이 곧 URL이 됩니다. 예: pages/sales/terms.vue → /sales/terms. 이걸 “파일 기반 라우팅”이라고 부릅니다.

05 / 16

요청이 처리되는 흐름

사용자가 링크를 하나 클릭했을 때, 화면에 데이터가 뜨기까지 내부적으로 어떤 순서로 일이 벌어지는지 살펴봅니다.

여기서 중요한 지점 두 곳을 짚어보겠습니다.

① nuxt.config.js의 proxy 설정

브라우저는 보안 정책(CORS) 때문에 다른 주소의 서버로 직접 요청을 보내기 까다롭습니다. 그래서 이 프로젝트는 브라우저가 같은 주소(localhost:5200)로 요청을 보내면, Nuxt 서버가 그 요청을 실제 API 서버(API_BASE_URL)로 대신 전달해주는 “중계소” 역할을 합니다.

nuxt.config.js
proxy: {
  '/api/v1': {
    target: process.env.API_BASE_URL,
    pathRewrite: { '^/api/v1': '' },
    changeOrigin: true,
  },
}

② plugins/axios.ts의 공통 인터셉터

모든 API 요청과 응답은 plugins/axios.ts를 반드시 거칩니다. 여기서 하는 일은 세 가지입니다.

단계하는 일
요청 전쿠키 인증을 위해 withCredentials를 켜고, 현재 채널(pc/mo)을 헤더에 실어 보냅니다.
응답 후서버가 내려준 result_cd 값을 검사해 세션 만료(EP), 권한없음(NA/BE), 서버오류(SE) 등을 공통으로 처리합니다.
에러 발생 시404는 에러 페이지로, 422/500은 세션 만료 처리로 자동 연결합니다.
✅

비개발자 관점 요약 — 화면마다 “서버 응답 확인하고 에러면 알림 띄우고…”를 매번 따로 짜지 않아도 되도록, 이 앱은 그 처리를 axios.ts 한 곳에 몰아두었습니다. 덕분에 페이지 코드는 “데이터 요청 → 화면에 뿌리기”에만 집중할 수 있습니다.

PC/모바일 자동 분기 — 이 프로젝트의 가장 독특한 부분

같은 화면이라도 PC와 모바일에서 레이아웃이 크게 다를 수 있습니다. 이 프로젝트는 “완전히 다른 두 벌의 화면”을 만들지 않고, 모든 페이지에 /pc 또는 /mo 접두어를 자동으로 붙여 같은 컴포넌트를 재사용하는 방식을 씁니다.

동작 원리 3단계

단계담당 파일내용
1nuxt.config.jsextendRoutes로, 정의된 모든 페이지 경로를 복제해서 /pc/…와 /mo/… 버전을 자동 생성합니다.
2plugins/router-prefix.js라우터가 실제로 이동하기 직전(beforeEach)에 끼어들어, 쿠키의 header_channel 값을 보고 접두어가 빠진 경로면 붙여서 되돌려 보냅니다.
3store/index.tsUser-Agent를 분석해 pc/mo/tablet을 자동 판별(utils/device.ts)하고, 그 결과를 전역 상태 device에 저장해 API 요청 헤더 등에도 활용합니다.
🧪

로컬 개발 환경의 특이사항 — localhost에서 개발할 때는 실제 사내 인증 시스템이 붙어있지 않기 때문에, router-prefix.js가 header_oamuser, header_channel 쿠키를 자동으로 심어줍니다. 화면 우측 하단에 뜨는 CookieDevTools 컴포넌트로 이 값을 직접 바꿔가며 PC/모바일 화면을 테스트할 수 있습니다.

상태 관리 (Vuex) — 앱의 공용 칠판

여러 컴포넌트가 동시에 알아야 하는 정보(로그인 사용자, 로딩 여부, 사이드바 열림 상태 등)를 각자 따로 들고 있으면 서로 어긋나기 쉽습니다. Vuex는 이런 정보를 한 곳(store)에 모아두고, 모든 컴포넌트가 같은 곳을 보게 만듭니다. 이 프로젝트는 store 파일 3개로 구성되어 있습니다.

파일보관하는 정보주로 쓰는 곳
store/index.ts로그인 사용자(user), 기기 종류(device: pc/mo/tablet), 전역 로딩 상태, 우측 사이드바 열림 여부Header, GlobalLoading, 모든 axios 요청
store/audio.ts현재 재생 중인 오디오 ID (한 번에 하나만 재생되도록 제어)HlsAudio.vue
store/relatedItems.ts지금 보고 있는 화면과 관련된 자료 목록(이미지·영상·PDF), 우측 패널의 선택 탭RightView.vue, design-bible/product-info

실제로 쓰이는 예: “오디오는 한 번에 하나만 재생”

여러 팟캐스트 카드가 화면에 동시에 떠 있어도, 사용자가 새로 재생 버튼을 누르면 이전에 재생 중이던 오디오는 자동으로 멈춥니다. 이건 각 오디오 컴포넌트가 서로를 직접 알지 못해도, store/audio.ts의 currentPlayingId 하나만 보고 있기 때문에 가능합니다.

store/audio.ts
// 재생 버튼 클릭 → 전역 상태를 내 id로 바꾼다
handleAudioPlay({ commit }, id) {
  commit('SET_CURRENT_PLAYING_ID', id)
}

// 각 플레이어는 전역 id가 "내 id"가 아니게 되면 스스로 멈춘다
watch: {
  globalPlayingId(newId) {
    if (newId !== this.id) player.pause()
  }
}

실시간 스트리밍 채팅은 어떻게 동작하는가

이 앱에서 가장 “AI스러운” 경험 — 답변 글자가 타이핑되듯 실시간으로 나타나는 효과 — 은 utils/stream-service.ts 하나가 담당합니다. ChatGPT 같은 서비스에서 익숙하게 보셨을 그 효과와 같은 원리입니다.

핵심 기술: ReadableStream

일반적인 API 요청은 “서버가 답변을 다 만든 뒤 한 번에” 돌려받습니다. 하지만 AI 답변은 만들어지는 데 몇 초~몇십 초가 걸릴 수 있어서, 다 만들어질 때까지 기다리면 사용자는 그동안 빈 화면만 보게 됩니다. 그래서 이 앱은 브라우저의 fetch API가 제공하는 ReadableStream 기능을 사용해, 서버가 글자를 만드는 족족 조각(chunk) 단위로 받아 바로바로 화면에 이어붙입니다.

utils/stream-service.ts
const reader = res.body.getReader()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  options.onChunk(decoder.decode(value))  // 조각이 도착할 때마다 즉시 화면에 반영
}

이 서비스를 쓰는 페이지는 product-info.vue(상품 Q&A), design-bible.vue(화법 생성·번역), CounselingComment.vue(상담멘트 재생성), under.vue(질병 인사이트) 총 4곳입니다. 사용자가 다른 화면으로 이동하면 stop()이 호출되어 진행 중이던 스트림 요청을 즉시 취소합니다.

에러 & 세션 처리

서버 응답이 실패하거나 세션이 만료됐을 때, 사용자에게 어떤 화면을 보여줄지를 정하는 흐름입니다.

상황처리 방식
서버 응답의 result_cd가 EP(세션만료)알림창 표시 후 첫 화면(/)으로 강제 이동
result_cd가 NA/BE (권한없음)403 에러 화면으로 이동
HTTP 상태 404“페이지를 찾을 수 없습니다” 에러 화면
HTTP 상태 422 또는 500세션 만료 처리와 동일하게 재접속 유도

실제 에러 화면은 layouts/error.vue가 그리며, 상태코드별로 제목·설명·버튼(홈으로/이전으로/다시시도)을 다르게 보여줍니다. pages/error.vue는 쿼리스트링으로 넘어온 상태코드를 읽어 Nuxt의 에러 시스템에 전달해주는 역할만 합니다.

용어 사전

문서 안에서 자주 등장한 개발 용어를 쉬운 말로 풀었습니다.

컴포넌트 (Component)
화면을 이루는 독립적인 부품 단위. 버튼 하나, 카드 하나처럼 재사용 가능한 조각.
props
부모 컴포넌트가 자식 컴포넌트에게 전달하는 데이터. “이 카드에 이 정보를 보여줘”라고 넘겨주는 값.
computed
다른 데이터를 조합해서 자동으로 계산되는 값. 원본 데이터가 바뀌면 자동으로 다시 계산됨.
watch
특정 데이터가 바뀌는 순간을 감지해서 원하는 동작을 실행시키는 기능.
라우팅 (Routing)
URL 주소에 따라 어떤 화면을 보여줄지 결정하는 시스템.
미들웨어 (Middleware)
페이지가 열리기 전에 먼저 실행되는 검문소 같은 코드. 인증 확인 등에 쓰임.
플러그인 (Plugin)
앱이 시작될 때 한 번만 실행되어 전역 기능을 준비해두는 초기화 코드.
프록시 (Proxy)
브라우저의 요청을 대신 받아 실제 서버로 전달해주는 중계 서버.
인터셉터 (Interceptor)
모든 요청/응답이 지나가는 길목에서 공통 처리를 해주는 관문.
스트리밍 (Streaming)
데이터를 한 번에 다 받는 게 아니라, 조금씩 나눠서 실시간으로 받는 방식.
SSR / CSR
SSR(서버렌더링)은 서버가 화면 HTML을 미리 만들어 보내는 방식, CSR(클라이언트렌더링)은 브라우저가 직접 화면을 그리는 방식. 이 프로젝트는 ssr: false로 CSR을 사용합니다.
목데이터 (Mock Data)
실제 서버 없이도 화면을 테스트할 수 있도록 미리 만들어둔 가짜 샘플 데이터.
목데이터 (Mock)
위와 동일 — 실제 데이터를 흉내낸 임시 데이터.
SCSS
CSS(디자인 언어)에 변수·함수 같은 프로그래밍적 기능을 더한 확장 언어.
Vuex / store
앱 전체가 공유하는 데이터를 한 곳에 모아두는 저장소.
